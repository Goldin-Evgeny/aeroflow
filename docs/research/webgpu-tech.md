# webgpu-tech

## Summary

Browser-based 3D LBM CFD is technically ripe as of mid-2026. WebGPU now ships by default in every major browser: Chrome/Edge since 113 (May 2023, desktop) and 121 (Jan 2024, Android), Firefox 141 (Jul 2025, Windows) with macOS added in 145/147 and Linux/Android expected during 2026, and Safari 26.0 (Sep 15, 2025) across macOS/iOS/iPadOS/visionOS — meaning iPhones/iPads finally run WebGPU. shader-f16 (half-precision, key for halving LBM memory/bandwidth) shipped in Chrome 120 and Safari 26 and is implemented in Firefox, though availability is GPU-dependent. Practical limits: spec defaults are 256 MiB maxBufferSize / 128 MiB maxStorageBufferBindingSize / 8 storage buffers per stage, but higher limits are requestable — per web3dsurvey field data, >=1 GB maxBufferSize is available on ~97% of WebGPU devices and ~2 GB on 79% (iOS caps near 1 GB); maxStorageBufferBindingSize of 1 GB is available on ~90%. Single buffers are capped at ~2 GB, but multi-gigabyte total allocations are possible by splitting DDF arrays across several buffers.

The open-source landscape: FluidX3D (ProjectPhysX, ~[13k+ stars], OpenCL desktop-only, no browser port) is the performance reference — D3Q19 at 93 B/cell (FP32) or 55 B/cell (FP16 compressed), 153 vs 77 B/cell/timestep, achieving 3,124 MLUPs on RTX 4060, 759 on Apple M1, 2,374 on M2 Pro — but its license is source-available NON-COMMERCIAL (commercial use requires negotiating with the author; derivatives inherit restrictions), so its code cannot be used in AeroFlow. Its key algorithms are freely re-implementable: the Esoteric Pull in-place streaming paper is open-access (MDPI Computation 2022, CC BY), and core LBM/BGK/D3Q19/Smagorinsky-LES methods are decades-old academic literature (caveat: Dassault/Exa PowerFLOW holds LBM patents on specific advanced techniques, e.g. transonic solvers — core low-Mach LBM+LES is safe). Existing browser WebGPU LBM work is embryonic: weblbm.pages.dev (D2Q9 only, D3Q19 'in progress'), huj31415's 2D demo, PPLUSCHT/LBM (Rust/WASM+WGSL, 2D-class), jinleili/fluid-webgpu, plus graphics-grade 3D fluid demos (Roquefort, SPH demos, compute.toys playground). No engineering-grade 3D LBM wind tunnel with forces/LES/wind-comfort output exists in the browser, and NO browser project publishes MLUPs benchmarks. Derived from bandwidth-bound scaling (verified FluidX3D per-cell traffic + verified 256 GB/s RTX 4060 Laptop bandwidth, assuming 60-85% of native efficiency in-browser, dispatch overhead 24-71 microseconds/dispatch is amortizable): a 256^3 grid (16.8M cells, 0.9-1.6 GB) should run ~60-85 timesteps/s in FP32 or ~120-165 with FP16 storage on an RTX 4060 Laptop; 512x512x128 is feasible on 8 GB GPUs with FP16; full 512^3 (7.4 GB FP16) only fits on high-memory Apple Silicon. These browser throughput estimates are calculated, not measured — no published browser LBM benchmark exists to confirm them.

## Facts

- [high] FluidX3D license forbids commercial use outright ('you may not sell this software, altered source versions, any part thereof'), forbids military use and AI training on the code; derivatives must be published and inherit all restrictions; commercial use requires a separately negotiated license from author Dr. Moritz Lehmann
  src: https://github.com/ProjectPhysX/FluidX3D/blob/master/LICENSE.md
- [high] FluidX3D D3Q19 needs 93 bytes/cell (FP32) or 55 bytes/cell (FP32/FP16 compressed), transferring 153 or 77 bytes/cell/timestep respectively; benchmark MLUPs: RTX 4060 = 3,124, RTX 3060 = 4,070, Apple M1 = 759, Apple M2 Pro = 2,374, Intel UHD 630 = 301; 8 GB VRAM fits a 534^3 grid in FP16 mode vs 288^3 for classic FP64 LBM
  src: https://github.com/ProjectPhysX/FluidX3D (README benchmark section)
- [high] The Esoteric Pull/Esoteric Push in-place streaming schemes (FluidX3D's core memory trick, halving DDF memory) are published open-access by M. Lehmann in Computation 10(6):92, 2022 (MDPI, CC BY) — the method is freely re-implementable even though FluidX3D's code is not reusable commercially
  src: https://www.mdpi.com/2079-3197/10/6/92
- [medium] Exa Corporation (now Dassault, PowerFLOW) holds numerous LBM-related patents including recently granted ones (e.g. US 12,118,279, 'Lattice Boltzmann based solver for high speed flows', granted 2024), so some specific advanced LBM techniques remain patent-encumbered; core BGK/D3Q19/LES methods from 1990s academic literature are not
  src: https://patents.justia.com/assignee/exa-corporation and https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12118279
- [high] No FluidX3D browser/WebGPU port exists; the most advanced browser LBM found is weblbm (https://weblbm.pages.dev/), a D2Q9 (2D) WebGPU implementation with D3Q19 listed as 'in progress'; other browser LBM projects (huj31415/lattice-boltzmann-webgpu, PPLUSCHT/LBM in Rust/WASM+WGSL, jinleili/fluid-webgpu) are 2D and/or publish no performance numbers
  src: https://github.com/topics/lattice-boltzmann; https://weblbm.pages.dev/; https://github.com/PPLUSCHT/LBM; https://github.com/huj31415/lattice-boltzmann-webgpu
- [medium] No published MLUPs benchmark for any browser-based 3D LBM was found in extensive searching — browser LBM performance for AeroFlow-class workloads is unmeasured territory as of July 2026
  src: Multiple searches (github.com/topics/lattice-boltzmann, web searches for 'MLUPS WebGPU browser') returned no browser MLUPs figures
- [high] WebGPU spec default limits: maxBufferSize = 268,435,456 B (256 MiB), maxStorageBufferBindingSize = 134,217,728 B (128 MiB), maxStorageBuffersPerShaderStage = 8, maxComputeInvocationsPerWorkgroup = 256, maxComputeWorkgroupStorageSize = 16,384 B; higher values must be explicitly requested via requiredLimits in requestDevice()
  src: https://developer.mozilla.org/en-US/docs/Web/API/GPUSupportedLimits
- [high] Field data (Web3D Survey): maxBufferSize >= 1 GB is requestable on ~97% of WebGPU-capable devices and ~2 GB (2147483647, the practical single-buffer ceiling) on 79%; iOS tops out around 1 GB (73%); maxStorageBufferBindingSize >= 256 MB on 97%, >= 1 GB on ~90%, ~2 GB on only 16% overall (92% on Windows, 64% on macOS)
  src: https://web3dsurvey.com/webgpu/limits/maxBufferSize and https://web3dsurvey.com/webgpu/limits/maxStorageBufferBindingSize
- [high] shader-f16 (WGSL half-precision) shipped in Chrome 120 (Dec 2023) on supporting hardware; Safari 26 ships f16 support (Apple's WWDC 2025 material highlights f16 as 'critical for iOS/visionOS, 50% memory reduction'); Firefox has implemented it; support is hardware-dependent and notably excludes many Qualcomm Android devices (gpuweb issue #5006)
  src: https://developer.chrome.com/blog/new-in-webgpu-120; https://dev.to/arshtechpro/wwdc-2025-webgpu-on-apple-platforms-16pa; https://github.com/gpuweb/gpuweb/issues/5006
- [high] Safari 26.0 shipped WebGPU enabled by default on September 15, 2025 across macOS Tahoe 26, iOS 26, iPadOS 26 and visionOS 26 — so by mid-2026 all iPhones/iPads on iOS 26 run WebGPU in Safari
  src: https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes; https://www.webgpu.com/news/webgpu-hits-critical-mass-all-major-browsers/
- [high] WebGPU ship status per gpuweb Implementation-Status wiki: Chrome 113+ (Win/Mac/ChromeOS), Chrome 121+ (Android, Jan 2024), Chrome 144+/147+ (Linux Intel Gen12+/NVIDIA Wayland); Firefox 141+ (Windows, Jul 22 2025), 145+ (macOS Apple Silicon), 147+ (all macOS), Linux/Android expected 2026; Safari 26+ all Apple platforms
  src: https://github.com/gpuweb/gpuweb/wiki/Implementation-Status; https://mozillagfx.wordpress.com/2025/07/15/shipping-webgpu-on-windows-in-firefox-141/
- [medium] Measured WebGPU per-dispatch API overhead is 24-36 microseconds (Vulkan backend) and 32-71 microseconds (Metal) — negligible for LBM if hundreds of timestep dispatches are batched per command-buffer submit
  src: https://arxiv.org/pdf/2604.02344 (Characterizing WebGPU Dispatch Overhead, 2026)
- [high] RTX 4060 Laptop GPU: 8 GB GDDR6, 128-bit bus, 256 GB/s memory bandwidth — bandwidth-bound LBM ceiling therefore ~1,670 MLUPs (FP32, 153 B/cell/step) or ~3,320 MLUPs (FP16 storage, 77 B/cell/step) before browser overhead
  src: https://www.notebookcheck.net/NVIDIA-GeForce-RTX-4060-Laptop-GPU-Benchmarks-and-Specs.675692.0.html + FluidX3D per-cell traffic figures
- [low] DERIVED estimate (no direct measurement exists): in-browser on an RTX 4060 Laptop, a 256^3 D3Q19 grid (16.8M cells; 1.56 GB FP32 or 0.92 GB FP16) should sustain roughly 60-85 timesteps/s (FP32) or 120-165 (FP16) assuming 60-85% of native bandwidth efficiency; 512x512x128 (33.5M cells) is feasible on 8 GB with FP16 at ~30-80 steps/s; full 512^3 (7.4 GB FP16) exceeds 8 GB cards and only fits on high-unified-memory Apple Silicon; Apple M4 Pro (273 GB/s) is in the same class as RTX 4060 Laptop, base M-series roughly 2-3x slower
  src: Calculated from FluidX3D bytes/cell/timestep (github.com/ProjectPhysX/FluidX3D) x verified GPU bandwidths; browser efficiency factor unverified
- [medium] compute.toys is a 'Shadertoy for WebGPU compute shaders' (WGSL playground) hosting fluid demos, but no 3D LBM demo with published performance was verifiable there; notable WebGPU 3D fluid demos (Roquefort smoke simulator, SPH/FLIP demos) are graphics-grade, not engineering CFD with forces/turbulence-model outputs
  src: https://github.com/compute-toys/compute.toys; https://bercon.github.io/roquefort/; https://tympanus.net/codrops/2025/02/26/webgpu-fluid-simulations-high-performance-real-time-rendering/
- [high] Autodesk Forma already sells browser-delivered 'rapid wind analysis' for architects using ML surrogate models (near-instant pedestrian wind comfort predictions) as pre-analysis, with slower cloud CFD for detail — evidence of demand for instant early-stage wind screening, but it is cloud/ML-based, not client-GPU CFD, and bundled inside Autodesk's platform
  src: https://blogs.autodesk.com/forma/2023/06/06/formas-rapid-wind-analysis-offers-instant-insights-into-wind-conditions/; https://www.autodesk.com/products/forma-site-design/environmental-impact-analysis
